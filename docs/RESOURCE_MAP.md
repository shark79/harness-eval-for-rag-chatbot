# Dify resource map

Checked **October 11, 2026**. This map covers the official resource families useful to a project; it is not a frozen inventory of every Marketplace provider. Start with a published Dify app and the Service API, then add knowledge, tools, and plugins as the workflow requires.

## Version and evidence baseline

- GitHub's [latest release](https://github.com/langgenius/dify/releases/tag/1.17.1) resolved to **1.17.1** during research. Its release commit is abbreviated `8387590` on GitHub. Recheck releases before choosing a deployment version.
- The repository tree, raw files and completed shallow clone were inspected at **`5fe7f018764e94aefa06f098a23e28a55d6b4e18`** on `main`. [Pinned tree](https://github.com/langgenius/dify/tree/5fe7f018764e94aefa06f098a23e28a55d6b4e18). A branch is not a release contract.
- [The documentation index](https://docs.dify.ai/llms.txt) separates Cloud, Self-Host, and developer resources, and publishes the Service API OpenAPI schema. Its recursive indexes were fetched directly when the browser fetch could not read them.
- [The docs repository](https://github.com/langgenius/dify-docs) says the public site hosts the latest docs; earlier versions use matching `release/*` branches. Check the target deployment's version, app mode, enabled features, and credentials before following a current page.

Native Agent apps and workspace Skills are documented, and Agent V2 and skill imports appear in 1.17.1 release notes. They should not be described wholesale as unreleased experiments. By contrast, the newer catalog-driven CLI and root `skills/` collection below are visibly different from the 1.17.1 CLI, and must be treated as **main-specific until compatibility is proven**.

## Platform and integration resources

| Resource | Practical project use | Primary source | Maturity / version caution |
| --- | --- | --- | --- |
| Core platform | Visual orchestration, model configuration, published AI apps, RAG and monitoring | [Dify repository](https://github.com/langgenius/dify) | Adopt a release tag; Cloud and Community/Enterprise capabilities differ. |
| Workflow and Chatflow | Repeatable task graphs or conversation flows with variables, branching and reusable nodes | [Workflow & Chatflow](https://docs.dify.ai/en/self-host/use-dify/build/workflow-chatflow) | Match node availability to the installed version. Use Workflow for task execution and Chatflow where conversation state is required. |
| Node reference | Choose LLM, retrieval, Code, HTTP Request, tools, iteration, loop, extraction, and output nodes | [Node index](https://docs.dify.ai/_llms/en/self-host.txt) | Code executes under the platform's sandbox limits; each node has its own typed inputs and outputs. |
| Human input and triggers | Pause for a person; start workflows through schedule, integration event, or webhook | [Human Input](https://docs.dify.ai/en/self-host/use-dify/nodes/human-input), [Triggers](https://docs.dify.ai/en/self-host/use-dify/nodes/trigger/overview) | Released features still need version checks. 1.17.1 disallows manually running trigger-entry workflows through ordinary run surfaces. |
| Native Agent apps / new Agent nodes | Configure one worker capability and use it in chat or within a workflow | [Agent overview](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/overview) | Separate from Legacy Agent apps and plugin-based agent strategies; confirm sandbox configuration and streaming support. |
| Workspace Skills | Publish reusable task instructions plus scripts/reference files for native Dify agents | [Skills](https://docs.dify.ai/en/self-host/use-dify/build/skills) | Library publication controls availability; current docs support ZIP/`.skill` imports. Local coding-agent skills are a different installation surface. |
| App DSL exports and templates | Version app graphs in project source and move configurations between workspaces | [App management](https://docs.dify.ai/en/self-host/use-dify/workspace/app-management), [Marketplace](https://marketplace.dify.ai/) | Export contains configuration and knowledge references, not dataset contents or usage logs. Secret environment values can be included if selected; inspect exports before committing. Rebind credentials, datasets and identifiers after import. |
| Public Service API | Call published app runs/chat, manage conversations/files, and integrate knowledge from a project backend | [API guide](https://docs.dify.ai/en/api-reference/guides/get-started), [OpenAPI schema](https://docs.dify.ai/en/api-reference/openapi_service.json) | Preferred documented application integration surface, with app-specific API keys and separate knowledge keys. Check endpoint support for the app mode and installed release. |
| Streaming and identity | Parse SSE events, maintain conversation identity, handle unfinished runs and Human Input pauses | [Streaming](https://docs.dify.ai/en/api-reference/guides/streaming), [End-user identity](https://docs.dify.ai/en/api-reference/guides/end-user-identity), [Human input API flow](https://docs.dify.ai/en/api-reference/guides/human-input-flow) | A connected stream does not prove completion. Preserve terminal status and stable server-side user identity; prevent raw API keys reaching browsers. |
| Knowledge APIs | Ingest documents, follow indexing progress, retrieve chunks, and manage metadata | [Knowledge API](https://docs.dify.ai/en/api-reference/guides/knowledge) | App keys and knowledge keys are not interchangeable. Dataset-scoped keys are described in 1.17.1; older keys may retain workspace-wide scope. |
| Ready-to-use and custom knowledge pipelines | Choose parsing, chunking, embedding, retrieval and datasource steps | [Knowledge](https://docs.dify.ai/en/self-host/use-dify/knowledge/readme), [Knowledge pipelines](https://docs.dify.ai/en/self-host/use-dify/knowledge/knowledge-pipeline/readme) | Test retrieval with representative questions before evaluating answer generation. Dataset schemas and pipeline plugins evolve. |
| External knowledge connector | Keep an existing retrieval system and expose its results to Dify | [External knowledge API](https://docs.dify.ai/en/self-host/use-dify/knowledge/external-knowledge-api) | This is a contract your service implements, not an interchangeable Dify dataset CRUD endpoint. |
| Integrations and model providers | Reuse supported providers and manage workspace credentials | [Integrations](https://docs.dify.ai/en/self-host/use-dify/workspace/plugins), [Model providers](https://docs.dify.ai/en/self-host/use-dify/workspace/model-providers) | Check model abilities, installed provider version and cost. Marketplace installation does not supply third-party accounts or credentials. |
| Tool plugins, OpenAPI tools, workflow tools, MCP | Connect reusable deterministic capabilities to an agent or workflow | [Tools](https://docs.dify.ai/en/self-host/use-dify/workspace/tools) | Workflow-as-tool has entry-type constraints. Current docs support HTTP MCP servers; verify transport/auth on the target release. Preserve MCP identifiers across workspaces. |
| Publishing and MCP export | Provide a hosted web app, embed it, or expose supported Dify applications through MCP | [Publishing](https://docs.dify.ai/en/self-host/use-dify/publish/README), [MCP publishing](https://docs.dify.ai/en/self-host/use-dify/publish/publish-mcp) | Importing MCP tools and publishing a Dify app as MCP are separate directions. Test access and applicable app-type restrictions. |
| Logs, analytics and traces | Inspect failed runs, token cost, latency and answer quality | [Logs](https://docs.dify.ai/en/self-host/use-dify/monitor/logs), [Monitoring integrations](https://docs.dify.ai/_llms/en/self-host.txt) | Select a trace provider only when needed. Verify retention, redaction and trace delivery rather than assuming all input is safe to log. |

## Project adoption order

1. Read [PROJECT_GUIDELINES.md](PROJECT_GUIDELINES.md) for the supplied support RAG use case. Its fictional [product guide](../knowledge/sources/product-guide.md) is the initial retrieval source; the [26-ticket CSV](../evals/datasets/support-tickets.csv) contains noisy baseline answers to evaluate, not material to ingest. Official Dify sources govern platform implementation; they must not silently replace the fictional fixture's business facts. Record the app type, host/version, approved model/provider and external systems before implementation. A live project deployment has not been verified.
2. Build one Workflow/Chatflow in the target instance, export a sanitized DSL, and prove the smallest backend-to-Dify-to-user result through the documented Service API.
3. Add knowledge only when the task needs grounded data; validate retrieval before tuning prompts. Reuse an existing tool/OpenAPI/MCP capability before authoring a plugin.
4. Add eval cases, error behavior, terminal streaming handling and traces. Keep source/DSL revisions and installed plugin versions with run evidence.
5. Adopt CLI/native agent automation only after testing the version and permission surface. Console operations require their own credentials and an explicit maintenance decision.

For work assignment, use the portable briefs in `agents/workers/` and the matching `.agents/skills/` procedure. The project skills guide the local coding assistant; importing them into Dify's native Skills library requires packaging, compatibility review and publication in that workspace.
